- routes.ts tickets: `status` query param goes into SQL as a parameter, but it's never checked against the enum, so a typo returns an empty page instead of a 400.
- bot/embeds/kit.ts:36 `bustUrl()` has no callers and points at crafatar, which returns 422 for names (verified: `crafatar.com/renders/head/Notch` → 422) even though the parameter is named `uuidOrName`. Delete it.
- bot/commands/changelog.ts:33,46: the Discord embed footer says `imperiummc.net`. Players see it.
- db/changelogStore.ts:51,56,66: published changelog text still says "ImperiumMC" and "English always stays at imperiummc.net". Players see it.
- README.md: titled "ImperiumMC Backend". It still describes Redis as the fallback through `BUS_TRANSPORT=redis` without warning that the live plugin doesn't listen there. Add "never set this".
- package.json: name `imperium-backend`, description "ImperiumMC backend API + Discord bot", version 1.0.0 placeholder.
- package.json: `cookie` is a dependency with zero imports. `@hono/zod-validator` 0.4 (latest 0.9.1) and `zod` 3 (latest 4.6) lag.

- changelogStore.ts:166: post ids use `Math.random()`. That's harmless for ids, but the repo replaced Math.random elsewhere on principle (routes.ts:3317, moderation.ts:122), so use `crypto.randomUUID()` for consistency.
- Redis/KV key names are still `ImperiumMC:*` (redis.ts:26-46, adminRegisterRoute.ts:27). They're protocol-locked to the plugin, so leave them, but document that in one place so nobody "fixes" one side.

## Pass 2 (agent)

> Second sweep over every `src/**` file on `master` @ `b76dc16` (2026-10-24), looking for things the docs above miss. Method: a scripted route inventory (146 routes with their middleware), greps for error shapes, fetch deadlines, floating promises and exports, a diff of `docs/api.md` against the routes, and a read of each flagged handler. Items marked **live** were checked against production or the PayNow Management API (read-only calls). Items already fixed in open PRs #10–#14 aren't repeated here.

### Outbound webhooks and PayNow wiring

- **live** PayNow store webhooks: `GET /v1/stores/{id}/webhooks` lists only `OnSubscriptionActivated`, `OnSubscriptionRenewed` and `OnSubscriptionCanceled` → `https://api.romanica.net/api/webhooks/paynow`. There's no `OnOrderCompleted`, `OnRefund` or `OnChargeback` subscription. So `fulfillPaynowOrder` (routes.ts:2438) and the refund path in PR #14 never receive an event. Whether one-time orders are fulfilled some other way (PayNow-side delivery commands) wasn't checked. This is the owner's call in the PayNow dashboard.
- webhooks/types.ts:47-52 `FEED_TYPE_MAP` expects `web_events.event_type` ∈ `player_rankup`, `player_prestige`, `war_result`, `season_roll`. The plugin only writes `contract_fulfilled`, `war_result` and `season_milestone` (`WebFeedPayloads.kt:21-23`, kotlin-migration-collab). As a result:
  - `player.rankup`, `player.prestige` and `season.roll` webhooks can never fire.
  - `war.result` reads `winner=` from the message (tailer.ts:50). The plugin's message is prose ("Your legion X won the war…"), so `winnerLegion` is always `'unknown'`.
  - The plugin writes one `war_result` row *per participant*, so one war emits N `war.result` deliveries.
- `GET /api/events/feed` filters on `contract_fulfilled`/`war_result`/`season_milestone` (community.ts:151), so the two `web_events` consumers disagree on the type set. docs/api.md:702-707 gives a third version: `uuid VARCHAR(36)` and `message VARCHAR(200)`, where the plugin DDL has `VARCHAR(32)` / `VARCHAR(255)` (`WebFeedService.kt:141-147`).
- tailer.ts:3-5 says "a gap larger than the 200-row window just means we skip un-emitted history". It doesn't skip anything: the cursor advances 200 rows per tick and catches up. A null cursor also replayed the whole feed (fixed in PR #13).

### Alerts and observability

- errorAlerts.ts:119,126,235: `alertError` fires the staff-webhook `fetch` and the owner-DM chain (up to 3 sequential Discord calls) as bare `void` promises, with no `waitUntil`. On Workers, work still pending after the response returns can be cancelled, so the alerts on the paths that matter most (onError at app.ts:140, `paynow-empty-order` at routes.ts:2449) can be dropped. cache.ts:71-77 already has a `waitUntil` helper for exactly this.
- **live** app.ts:6-7: `GET /health` returns `{"version":"dev","deployedAt":"1970-01-01T00:00:00.000Z"}` on prod. `DEPLOY_VERSION` is set nowhere (no `define`, no var), and `new Date()` at module scope is the epoch on Workers. The comment at app.ts:83-85 says it reports "the actual deploy stamp baked at build time". app.ts:81: `GET /` hardcodes `version: '1.0.0'` (live: same).
- Floating writes without `waitUntil`: guides.ts:106 (view counter), auth/apiKeys.ts:132 (`last_used_at`), bot/moderation.ts:62 (mod-log outcome), db/pool.ts:245,255 (discord→uuid cache warm/**delete**). The pool.ts:255 delete matters most. If it's dropped, an unlinked Discord user still resolves to the old uuid through the 24h Redis fallback (pool.ts:178) whenever Postgres is down.

### Error shapes and status codes

- v2/respond.ts:3-5 says every v2 response is enveloped (`{ error: { code, message } }`, closed enum). Only crashReports, gallery and leaderboards use `fail()`. The rest return plain `{ error: '<prose>' }`: adminPanel (6), dms (11), guideComments (12), guides (18), keys (7), moderation (2), storeOrders (2), tickets (17). `requireStaffRole` (gates.ts:537,543), mounted on v2 admin, does the same. Clients can't branch on a code for most of v2.
- routes.ts:2683: `POST /api/tickets/:id/respond` binds the raw `:id` against `support_tickets.id BIGSERIAL` (migrate-tables.cjs:49). A non-numeric id throws Postgres `22P02`, which goes to app.onError → 500 **and a staff alert** instead of 400/404. v2 `PATCH /tickets/:id` and `POST /tickets/:id/notes` (v2/tickets.ts:153,185) return 500 "Ticket update failed" for the same input.
- v2/tickets.ts:73 returns 429 for "2 open tickets". It's a business-rule limit, not rate limiting; 409 fits better. The extra `code: 'TICKET_LIMIT'` isn't in the v2 enum.

### P1c: `CLIENT_FOUND_ROWS` and the nonce guard (investigated, not fixed)

- db/mysqlWire.ts:328,335 sends `CLIENT_FOUND_ROWS` in the handshake. db/busMysql.ts:91-98 `busKvPutOnce` claims a nonce with `INSERT … ON DUPLICATE KEY UPDATE kv_key = kv_key` and treats `affectedRows === 1` as "first sighting".
- MySQL/MariaDB document ODKU affected-rows as 1 = inserted, 2 = updated, 0 = existing row unchanged, **except that with `CLIENT_FOUND_ROWS` the unchanged case reports 1**. On the default transport, a replayed nonce would therefore read as first sighting, and `claimNonceOnce` (db/redis.ts:185-199) would always return true. The Node dev path is affected too: mysql2's default flags include `FOUND_ROWS`.
- The other `affectedRows` consumer, `busKvConsume` (busMysql.ts:77-88), isn't affected: its UPDATE always changes `expires_at`, so matched = changed.
- Impact today: the only consumer is `adminRegisterRoute.ts:63`. A captured HMAC-signed request can re-run the idempotent command-registration PUT within ±120s. `atomic-consume.test.ts` forces `BUS_TRANSPORT='redis'`, so no test covers the MySQL path.
- **Why no fix PR:** this needs real server semantics to prove. There's no MySQL/MariaDB on the agent machine, downloading one needs owner approval, and the live game DB is off-limits. A test against a hand-written fake server would only restate the docs.
- **Proposed fix:** drop `CLIENT_FOUND_ROWS` from the caps (nothing reads matched-vs-changed) and set `flags: '-FOUND_ROWS'` on the mysql2 pool.
- **Verification:** against any real MariaDB, run `busKvPutOnce('k', 60)` twice. Expect `true, true` today and `true, false` after the fix. Then do the same two-request replay as `admin-register-nonce.test.ts` without the redis override.
